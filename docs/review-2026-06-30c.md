## Per-point findings

### 1. レイアウト／算術 — ✅ 正しい（境界外アクセスなし）

- `ENTRIES_PER_DIR_PAGE = (4096-4)/4 = 1023`。request の主張と一致。
- 最終スロット `slot=1022`：`entry_offset = 4 + 1022*4 = 4092`、`[4092..4096]` で**ページ内
  ぴったり**。`slot=1023` は `entry_offset=4096`→範囲外だが、`slot = i % 1023` は常に
  `0..=1022` なので**到達不能**。
- `[off..off+4]` スライスは全て4バイト境界で、`copy_from_slice`/`try_into` も4バイト固定。
  アラインメント問題なし（CLAUDE.md の手書きバイト操作要件を満たす）。
- reviewer テスト `exact_directory_page_slot_boundary` で `ENTRIES_PER_DIR_PAGE-1`（第1ページ
  最終スロット）と `ENTRIES_PER_DIR_PAGE`（第2ページ先頭）が別ページに正しく分かれることを固定。

### 2. 密度不変条件 — ✅ 保たれる（穴は通常操作で発生しない）

- **`push` が唯一の public mutator**。`set` は private で、`push` は常に `logical = self.len`
  → `set` → `len += 1`。よって `logical > len` の飛ばしは公開 API から発生せず、`set` 内の
  `logical > self.len` → `StorageCorrupted` ガードは防御的に正しい。
- probe（`probe_overclaimed_len`）：`with_root(root, 5)` で実書き込み1件のみの状態でも
  `resolve(3)` は `Ok(None)` を返し**穴を graceful に扱う**（panic/誤読なし）。
  → 通常操作で穴は作れず、壊れたメタデータからの復元時も None に縮退するだけ。**latent bug
  ではない**（§5 で len 永続化規律を Phase 2 で固める前提なら問題なし）。

### 3. 永続化／復元 — ✅ 強化済み（マルチページ復元を追加）

- 既存 `with_root_restores_mapping` は 2 エントリ（単一ページ）のみ。request の指摘どおり
  **ディレクトリページ境界をまたぐ復元が未カバー**だった。
- reviewer テスト追加：
  - `with_root_restores_across_directory_page_boundary`：`ENTRIES_PER_DIR_PAGE*2+3` 件を
    push → `with_root(root,len)` で復元 → 第1/2/3ページと両境界の全点が正しく resolve、
    `resolve(n)` は None。
  - `push_resolve_roundtrip_multipage`（proptest, 1..ENTRIES_PER_DIR_PAGE*3 件）：
    全 logical が push 値に一致、`i>=N` は None。PROPTEST_CASES=1000 でも green。

### 4. キャッシュ／WAL 挙動 — ✅ オンディスクのみ（desync リスクなし）、hand-off は明確

- directory ページは全て `read_page`/`write_page` 経由（`resolve`/`set`/`ensure_dir_page`/
  `append_blank_dir_page`）。**page 外の可変状態を持たない**ため、WAL write-through と
  rollback（`file.rs` restore の `cache.clear()` + WAL truncate）に自動で乗る。設計 §11.3 の
  「インデックスは全てオンディスク」前提と整合。
- `{root, len}` は struct 内（オンディスク未永続化）。これは request どおり **Phase 2/4 の
  header 永続化の仕事**。`with_root(root, len)` という復元 API が既にあり、hand-off は明確
  （header に2フィールド足して open 時に `with_root` を呼ぶだけ）。曖昧さなし。
  - 記録：Phase 2 で len を header に永続化する際は、`alloc_*_slot` が node_page_count を
    WAL 経由で header 書き戻すのと同じ規律（crash-without-flush 耐性）を踏襲すること。

### 5. `UNMAPPED` エイリアス — ⚠️ 実害なし、ただし `push` に番兵ガードがない（before release）

- `0xFFFF_FFFF` を物理 pid として持つには ~2^32 ページ = 16TB+ のファイルが必要で、設計の
  到達目標（数億〜数十億ノード）では**現実的に到達不能**。aliasing の実害はない。
- ただし probe（`probe_push_unmapped_value`）で確認：`push(UNMAPPED)` は `len` を進めるが
  `resolve` は `None` を返す＝**マップ済みなのに不可視**になる。`push` はこの値を弾かない。
  - 分類：**Before release**。実害は無いが、`push` に `physical != UNMAPPED` の `debug_assert`
    か guard を入れて不変条件を明示すると、将来 free-list で pid 再利用が入った時の事故を防ぐ。
    Phase 1 のマージ自体は妨げない。

### 6. エラー処理／スタイル — ✅ 規約準拠、`unwrap_or([0xFF;4])` は妥当

- `unwrap()`/`expect()`/`unsafe` なし。`read_link`/`read_entry` の
  `try_into().unwrap_or([0xFF;4])` は **4→4 バイトの infallible 変換**（スライス長は常に4）。
  到達不能な失敗枝に番兵 `[0xFF;4]`（= `UNMAPPED`）を返すのは、万一にも壊れた読みを「unmapped /
  end-of-chain」へ縮退させる安全側の選択で妥当。`?` 伝播でも良いが、ここは clippy 的にも
  `unwrap()` 回避として一貫しており **現状の選択を支持**。
- corruption probe（`probe_offend_next_link`）：off-end の next link は memory backend で
  `Err(StorageCorrupted(999999))`、file backend では `read_exact` の `UnexpectedEof`→`Io` で
  **clean error（panic/loop なし）**。reviewer テスト `corrupt_offend_next_link_errors_cleanly`
  で恒久化。

## Extra findings

- **E-1（cycle は無限ループしないが silent 誤読）**：probe（`probe_cycle_chain`）で root.next=root
  の自己ループを注入 → `dir_page_pid`/`ensure_dir_page` のチェーン走査は **`for _ in 0..dir_index`
  の有界ループ**なので**ハングしない**（cycle でも dir_index 回で停止）。ただし停止後に誤った
  ページへ着地し `Ok(Some(wrong))` を silent に返す。チェーンは `ensure_dir_page` だけが構築し
  外部書き込み経路は無いため、これは corruption 限定シナリオ。
  - 分類：**Record only**。有界ループでハング・panic は無いので Phase 1 は問題なし。将来
    corruption 検出を厚くするなら「歩数 > 期待ページ数で StorageCorrupted」を入れる余地（plan へ）。

- **E-2（テストヘルパの page 0 前提）**：テストの `file()` は page 0 を header 代用として
  append し pid 1 から directory が始まる。実 DB の page 0 予約と一致しており妥当。Phase 2 で
  topology 接続時、directory ページと topology/property ページの physical 割り当てが
  `append_page` 単一カウンタを共有する点（混在 append）は Phase 2 レビューで確認すべき（記録）。
