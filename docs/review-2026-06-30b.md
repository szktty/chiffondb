## Per-finding re-check

### C-1（property RID の非対称, → §3.4）— ⚠️ 決定は妥当だが §4 と矛盾＋成立条件が未記載

**応答内容**: §3.4 を新設し「(b) property RID は物理維持、Phase 3 で再判断」を暫定決定。

**実コード照合**:
- `PropertyStore::write`/`write_raw` が物理 pid を RID として返す点は事実（`value.rs:160,170,
  181,199,208,217`）。§3.4 の現状説明は正確。
- **「固定境界を撤廃しても物理 pid 参照は壊れない」は条件付きで真**。確認すべきは blob チェーン
  の読み出し：`PropertyStore::read`/`read_raw` は次ページを **`pid = first_pid + next`（相対
  オフセット）** で辿る（`value.rs:235,266`）。これはチェーン構成ページが**物理的に連続して
  append された**ことに依存する。`write` は `append_page` を連続実行するので現状は連続。
  → 固定境界を撤廃しても property を `append_page` で末尾に伸ばし続ける限り連続性は保たれ、
  (b) は成立する。**ただしこの「物理連続が (b) の成立条件」が §3.4 に書かれていない**。
  将来 free-list 再利用（§7）で property ページが非連続に割り当てられると、相対オフセット
  チェーンは即座に壊れる。(b) を選ぶ前提として明記すべき。

- **❗ 内部矛盾（D-1）**: §4 影響表は
  `| storage/value.rs | property ページ確保が固定 prop_start 前提 → directory 経由へ |`
  のまま。§3.4 で (b)（物理維持・directory 非経由）を選んだのだから、この行は (b) と矛盾する。
  (b) なら value.rs の変更は「`prop_start..page_count` スキャンの起点を固定値から外す／property
  も単純 append にする」であって「directory 経由へ」ではない。§4 の value.rs 行を §3.4 の決定
  （物理維持）に合わせて書き換えるべき。

  なお §4 表の `db.rs`「セグメント事前確保（pages 1..prop_start の zero-fill）の撤廃」
  （`db.rs:54-61,73-78`）は (b) でも正しい（事前確保は不要になる）。矛盾は value.rs 行のみ。

### C-2（find が &str で PropertyPath 非経由, → §11.2「検索 API 拡張」）— ✅ 解決

**応答内容**: §11.2 に「`find`/`find_all` のキーを `&str`→`PropertyPath` に変更、`From<&str>`
で平坦キー callers は維持、索引あり→B+tree／無し→スキャンフォールバック」を追記。

**実コード照合**:
- `From<&str>`／`From<String>` は両方実在（`command.rs:127,133`）。平坦キー callers が
  `.into()` で渡せるのは正しい。
- 現状 `find` の**プロダクション呼び出し側は限定的**で網羅できる：
  - `index::find` → `db.rs:1001`（`find_node_by`）の1箇所のみ。さらに `find_node_by` の
    呼び出しは `db.rs:1056`（`GraphAccess::find_node` trait 実装）。
  - `index::find_all` → プロダクション呼び出しはゼロ（テストのみ）。
  - FFI/API 層は `GraphAccess::find_node(&str, &str, &Value)` 経由。trait シグネチャは `&str`
    のまま保ち内部で `.into()` 変換すれば **trait も callers も壊れない**。設計の「スキャン
    フォールバック」プランは現行 callers を全てカバーする。
- → C-2 は解決。追加注文なし（trait シグネチャを変えずに内部変換する方針を実装時に採れば
  互換は完全。記録のみ）。

### C-3（ラベルインデックス＝primary のみ, → §11 層1「全ラベル(b)」）— ✅ 解決・実装可能

**応答内容**: §11 層1 に「マルチラベル／動的ラベルの扱い」小節を追加し、(a) primary のみ／
(b) 全ラベル を提示、**暫定 (b) 全ラベル**、`rids_of_type` の primary-only callers への影響は

**実コード照合**:

  CoW への更新規律切り替えは MVCC 実装時の必須作業」は前回レビュー指摘どおりで、正しい。
- **§11.3「インデックスは全てオンディスクに置く」前提 — ✅ 実在の制約（過大主張でない）**。
  ロールバックは `restore`（`file.rs:540-558`）が WAL truncate＋`cache.clear()`＋header revert
  で行う。`restore` は page-cache 以外の任意の in-memory 補助構造を知らないため、インデックスを
  page 外のメモリに持つと rollback で乖離する。「page 上に置けば WAL で一緒に巻き戻る」は正しく、
  逆条件（メモリ持ちは巻き戻らない）も正しい。未決6 との連動も妥当。
- **§4 テスト境界の列挙 — ✅ 完全**。全 grep で確認した境界依存サイトは
  `value.rs:150,189` / `db.rs:54-61,73-78`（事前確保）/ `db.rs:2867`（テスト容量計算）/
  `index.rs:102-105`・`pathfinding/mod.rs:239-242`（make ヘルパ 1..64）/ `commands/info.rs:14-16`。
  §4 の列挙はこれらを**全てカバーしており漏れはない**。これ以外に境界前提のサイトは存在しない。

## Extra finding（記録のみ）

- **E-1**: `rid_to_id`（`db.rs:1046`）は外部 NodeId を `(page_id << 16) | slot_id` で構成。
  論理ノードページ番号を上位ビットに 16bit シフトで埋めるため、論理ページ番号が `2^48` を
  超えると衝突する。設計目標（数億〜数十億ノード＝論理ノードページ ~数千万）では `<<16` しても
  2^48 以内で安全。u64 化（§7）や将来の桁拡大時には NodeId エンコードの見直しが要る——記録のみ
  （本ブランチのスコープ外、merge を妨げない）。
