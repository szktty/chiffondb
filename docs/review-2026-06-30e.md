## Per-point findings

### 1. Blob relink correctness — ✅ 正しい（2ページ／≥3ページ両方 probe 済み）

- レイアウト（`property.rs`）：chain page = `[0..4] next` `[4..8] chunk_len` `[8..] data`
  （`CHAIN_HEADER_SIZE=8`, `CHAIN_DATA_PER_PAGE=4088`）。
- `write_blob_chain` が相対 index で `next` を書く → `relink_chain_to_logical` が `[0..4]` のみを
  論理番号へ上書きし `[4..8]`/data は保持 → read は `[0..4]`（論理 next）を辿って順にページ収集 →
  `read_blob_chain_dense` が `next` を無視し収集順に `[8..8+chunk_len]` を連結。**収集順と連結順が
  一致**し、relink 後に相対 next を読む経路は無い。
- probe：4098B（ちょうど2ページ）round-trip 一致。既存 `random_blob_roundtrip` / 新規
  `large_blob_spans_chain_and_roundtrips`（~3ページ, slot=`CHAIN_HEAD_SLOT`, prop_count≥3）も green。

### 2. Single source of truth — ✅ stale window なし

- `DatabaseFile` は directory struct を保持せず、毎操作で `property_dir()`（header から構築）→
  操作 → `store_property_dir()`（header へ書き戻し）。
- `alloc_property_page` は `append_page` → `dir.push`（directory ページ書き込み）→
  `store_property_dir`（root/len を header へ）を**1メソッド内で完結**。push 後に必ず
  store_property_dir が走る。複数 alloc をまたぐ logical 操作（blob chain）でも各 alloc が個別に
  header を更新するので、途中状態でも header は常に「実際に push 済みの len」を指す（過剰主張なし）。

### 3. WAL / rollback — ✅ 3つ（append_page / push / write_header）が一緒に巻き戻る

- probe（clean tree）：snapshot 直後 `(root,len)=(0xffffffff,0)` → property write 後 `(0x2,1)` →
  `restore(snap)` 後 `(0xffffffff,0)` に**完全復帰**。
- 仕組み：`FileSnapshot` が header 全体を保持（`file.rs` の既存規律。`property_dir_root`/`_len` も
  header フィールドなので revert 対象に自動的に入る）+ WAL truncate（append された物理ページ・
  directory ページを破棄）+ `cache.clear()`。新規 property 成長は原子的に unwind する。
  - 補足：恒久テスト（rollback 専用）は本レビューでは追加していない。既存 WAL/rollback テスト
    （`file.rs` の `rollback_via_wal_truncate_discards_writes` 等）と上記 probe で挙動は確認済み。
    Phase 2b で topology を directory 経由にした後、**node/edge 成長 + property 成長を同一 tx で
    rollback する統合テスト**を入れると望ましい（Needs a test、下記）。

### 4. `is_valid()` 依存 — ✅ 依然必要かつ正しい

- 小値パスは `0..property_page_count` を走査して空きスロットを探すが、property directory には
  **slotted-page（小値）と blob-chain ページの両方**が登録される（各 blob chunk も
  `alloc_property_page` でマップ）。よって走査中に blob-chain ページに当たり得る。
- `SlottedPage::is_valid()`（`property.rs:48`）は slot ディレクトリの境界整合を検査し、blob-chain
  ページを「無効」と判定してスキップする。→ **小値走査が blob ページを誤って slotted として
  読む/壊すのを防ぐガードとして現役**。撤去不可。正しい。

### 5. `property_page_count` を read limit に使う — ✅ 安全な上界

- chain pages は全 property pages の部分集合なので chain 長 ≤ `property_page_count`。
- `read_property_bytes` の chain walk は `if pages.len() > limit { StorageCorrupted }`。`>` なので
  ちょうど `limit` 枚までは許容し、それを超えたら（= cycle/corruption）エラーで停止。無限ループ
  しない。上界として安全。

### 6. `unwrap_or` on slices — ✅ `page_directory.rs` と同じ意図的パターンで妥当

- `read_property_bytes` の `try_into().unwrap_or([0xFF;4])`（→ end-sentinel に縮退）、
  `read_blob_chain_dense` の `try_into().unwrap_or([0;4])`（→ chunk_len 0 に縮退）はいずれも
  **4→4 バイトの infallible 変換**。到達不能枝に安全側の既定値を返す Phase 1 と一貫した方針。
  `unwrap()` 回避（CLAUDE.md 規約）にも合致。支持。
