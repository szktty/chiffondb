## Summary

設計の中核的主張は概ね実コードと整合する。容量算術（~2000 → u32 空間）は正確、
topology の `RecordId.page_id` が論理であることも確認できた。独立 directory・後方互換放棄・
MVCC フィールド統合という決定はいずれも内部的に一貫している。

ただし**設計の前提に実コードとのギャップが3点**ある。いずれも「設計が現状コードをこう説明
している／こう流用できると言っている」部分が、実際の現状コードと食い違う。実装に入る前に
設計ドキュメント側で明示・解消すべき。結論は **approve-with-changes**（容量拡大の主目的＝
Phase 1–3 はそのまま進めてよい。下記 C-1〜C-3 を設計に反映してからインデックス段へ）。

## Per-point findings（依頼の検証項目順）

### 1. 容量算術（§1/§2）— ✅ 正確

`page.rs` の `compute_slot_count`：`NODE_RECORD_SIZE = 64` で
`n = 4096/(64+1) = 63`、`bitmap_bytes(63)=8`、`8 + 63*64 = 4040 ≤ 4096` → **node 1ページ63
スロット**。設計の「~63スロット」と一致。

`topology.rs` の `node_capacity = (seg_end - topo_start).div_ceil(2)`。デフォルト
`seg_end=64, topo_start=1` → `63.div_ceil(2) = 32` ページ。`32 × 63 = 2016 ≈ 約2000` で
設計の主張どおり。`alloc_node_slot` は `logical >= node_capacity()` で
`CapacityExceeded` を返す（`topology.rs:388`）。

u32 論理空間の上限 `2^32 × 63 ≈ 2700億` も `RecordId.page_id: u32`（`page.rs:13`）と整合。
「現実的には数億〜数十億」も `node_page_count` が u32（§7 で u64 化を future work）で頭打ち
という説明と一貫。**この項目は修正不要。**

### 2. `RecordId.page_id` は論理（§1「重要な既存事実」）— ⚠️ topology は正、ただし限定的

topology については主張どおり：`alloc_node` は `RecordId::new(logical as u32, slot.0)`
（`topology.rs:173`）で論理番号を格納し、`read_node`/`write_node` は `node_pid(logical)` で
物理変換（`topology.rs:66-72, 192, 207`）。外部公開 RID は確かに論理アドレスであり、
directory 間接化で**ノード／エッジの**識別子の意味は変わらない。

**しかし C-1 を参照**：property の RecordId は論理ではなく物理であり、設計はこの非対称性に
言及していない。

### 3. 影響リスト（§4）の網羅性 — ⚠️ 概ね網羅、テストコードの漏れ

`property_segment_start` 等の境界依存サイトを全 grep した結果、§4 が挙げる
`value.rs`（blob ページ確保 `value.rs:150,189`）・`db.rs`（セグメント事前確保
`db.rs:56-61,73-78`）・`commands/info.rs:14-16` はカバー済み。

漏れ（影響表に出ていない境界依存コード）：
- **`db.rs:2867` のテスト** `insert_node_returns_error_when_node_capacity_exceeded` が
  `(property_segment_start - topology_segment_start).div_ceil(2)` を直書きしている。
  `node_capacity` 撤廃時にこのテストは書き換え／削除が必要。
- `topology.rs` 内テストの `make_store()`（`for _ in 1..64`, `TopologyStore::new(1, 64)`）と
  `index.rs` の `make()` も固定セグメント前提。directory 化で初期化フローが変わる。

→ 致命的ではないが、§4 に「テストの境界前提も改修対象」を一行追加すべき（**C-3**）。

### 4. インデックス設計の健全性（§11）— ⚠️ 重大な前提ズレ2点

#### (a) `PropertyPath::resolve` 流用（§11.2）の semantics — ✅ resolve 自体は設計どおり

`command.rs:100-115` の `resolve`：`Flat` は `props.get(key)`、`Path` は `Value::Object` を
walk し非オブジェクトに当たると `None`。設計の「スカラー終端のみ／配列非対応／`None` 除外
（部分インデックス相当）」は resolve の実挙動と**正確に一致**。doc comment
（`command.rs:85-86`）も「array indexing is out of scope」と明言。

#### (b) しかし現状の `find`/`find_all` は `PropertyPath` を使っていない — ❗ **C-2**

§11 層2 は「`find` / `find_all` を加速」「インデックスキーは `PropertyPath` を流用」と書くが、
`index.rs` の `find`/`find_all`/`props_match` は **`key: &str` を取り `props.get(key)` で
平坦キーのみ照合**（`index.rs:23-25, 44-90`）。`PropertyPath::resolve` は経由しない＝
**現状の検索はネストキーに非対応**。

つまり設計は「既存 `find` を `PropertyPath` インデックスで置き換えれば semantics は保たれる」
ように読めるが、実際にはインデックスのほうが**現状検索より表現力が広い**（ネスト対応）。
これは矛盾ではないが、設計が「現状の `find` semantics と整合」と暗黙に前提している点が
不正確。「層2導入時に `find` API を `PropertyPath` 受けに拡張する」ことを設計に明記すべき。

#### (c) ラベルインデックス（層1）とマルチラベルの不整合 — ❗ **C-1 と並ぶ重大点**

設計 §11 層1 は「`type_id → ノード RecordId 集合`」。だが現状ノードは primary
`node_type_id` に加え `label_ref` 経由の**追加ラベル（マルチラベル／動的ラベル）**を持つ
（`record.rs:60`, `db.rs:830 insert_node_with_dynamic_labels`, `db.rs:727 get_node_type_ids`）。

一方で現状の `list_nodes`/`count_nodes`/`rids_of_type` は **primary `node_type_id` のみ**で
フィルタし、追加ラベルでは絞らない（`index.rs:36`, `db.rs:368-370`）。

→ 層1 を「ノードの全ラベル → 集合」で索引すると、追加ラベルでもヒットして**現状の
`list_nodes` より広くマッチ**し挙動が変わる。逆に primary type だけ索引すると動的ラベルで
引けない。**どちらの semantics を採るか**を設計で決める必要がある（現状踏襲＝primary のみ、
が無難だが「ラベルインデックス」という呼称と乖離する）。設計はこの分岐に触れていない。

#### (d) 一意制約（層3）— ✅ 方針は妥当

`(型, キー) → ノード` の一意版という位置づけは標準的。新 `GraphError` 変種追加も
`error.rs` の既存スタイル（`thiserror`）に乗る。`@unique` の DSL 追加余地も
`field_def`（`schema.pest:28`）／`FieldDef`（`ast.rs:36`）にあり問題なし。
ただし `extends`（継承, `schema.pest:14`）がある型での一意制約の継承範囲は実装時に要決定
（記録のみ）。

### 5. MVCC マージリスク（§6）— ⚠️ 方向性は一貫、ただし「自動的に発展する」は楽観的

`ARCHITECTURE.md:165-169` は `page_directory_root` を「per-transaction page directory
(logical→physical), snapshot isolation, SWMR」用に予約（常に0）。設計 §6 は恒久 directory に
再利用し将来 CoW root に発展させる。

**評価**：方向性は coherent。恒久 directory（単一の現在マッピング）は MVCC で root が指す
「現在のツリー」そのものになり得るので、フィールド再利用が将来の MVCC を**閉ざしはしない**。

**ただし楽観の指摘**：現状の永続化は **WAL write-through の in-place 上書き**
（`file.rs:244-263` の `write_page` は同一 pid を上書き）。MVCC スナップショット分離の本質は
CoW（既存ページを書き換えず新ページに書いて root を差し替える）で、現状モデルと根本的に
異なる。恒久 directory を入れても **directory エントリを in-place 更新する限り MVCC にはなら
ない**。「directory があれば CoW の前提」は正しいが、「恒久 directory がそのまま MVCC root に
育つ」には *エントリ更新を in-place→CoW へ変える* 大転換が残る。フィールド再利用はそれを
阻害しないが解決もしない。§6 に「統合は将来の MVCC を阻害しないが、CoW 更新規律への移行は
別途必要」と but-clause を足すと正確になる（設計判断の (i) 統合自体は支持）。

### 6. 整合性 & WAL（§11.3, §8 open item 6）— ⚠️ 条件付きで保証される

`§11.3`「インデックス更新が同一 WAL write-through に乗りロールバックで一緒に巻き戻る」は、
**インデックスを通常のオンディスクページ（`read_page`/`write_page` 経由）として持つ限り**
成立する。ロールバックは `restore`（`file.rs:540-558`）が WAL truncate + page-cache clear +
header 全体 revert で行うため、ページ上のインデックスも自動で巻き戻る。

**注意すべきギャップ**：
- `FileSnapshot` の規律コメント（`file.rs:325-330`）が明示するとおり、**header に足すフィールド
  は rollback で revert される前提**。directory root を header に置くのは整合的（revert される）。
- だが §8 未決5「ホットなルート段を別持ちするか」で**page-cache 外の in-memory 構造**に
  インデックス／directory の一部を載せると、それは WAL にも snapshot にも乗らず**ロールバックで
  巻き戻らない**。`restore` は `cache.clear()` はするが任意の in-memory 補助構造は知らない。
  → §11.3 の保証は「全部ページ上に置く」前提に**依存**する。設計にこの前提条件を明記すべき
  （未決5の決定が §11.3 の正しさを左右する、という依存関係）。

## Extra findings（依頼項目外で気づいた点）

- **E-1（property RID の物理性, C-1 の核）**：`PropertyStore::write`/`write_raw` は
  `RecordId::new(pid, slot.0)`（`value.rs:160,170,181,199,208,217`）で**物理 pid**を返し、
  これが `node.property_ref` としてレコードに永続化される（`record.rs:69`）。topology RID は
  論理だが property RID は物理、という非対称が現状存在する。§3 で property も directory 経由に
  すると述べる（§4 表 `value.rs` 行）が、**既存 property_ref が物理 pid を保持している事実**と
  「directory 化で物理配置を自由にする」ことの関係（新規 property RID を論理化するのか、物理の
  まま directory を介さず append し続けるのか）が設計で未定義。後方互換なしなので旧ファイルは
  問題にならないが、新フォーマットでの property RID の意味を §3 で決める必要がある。

- **E-2**：`alloc_node_slot` は新規論理ページ確保時に `node_page_count` を header に書き戻し
  WAL 経由で永続化（`topology.rs:401-405`）。directory 化後も「directory 拡張 → root/エントリ
  を WAL 経由で永続化」を同じ規律で行えば crash-without-flush 耐性は保てる。設計 Phase 1 の
  「チェーン拡張」テストでこの永続化規律（カウント／root の header 書き戻し）を必ず covered に。

## 設計に反映すべき変更（Changes required before索引段）

- **C-1（Must address in design）**：property RecordId が**物理 pid**である非対称性（E-1）を
  §2/§3 に明記し、新フォーマットでの property RID の意味（論理化 or 物理維持）を決める。
- **C-2（Must address in design）**：現状 `find`/`find_all` は `PropertyPath` 非経由・平坦キー
  のみ（`&str`）。§11 に「層2導入時に検索 API を `PropertyPath` 受けへ拡張する」ことを明記し、
  「現状 semantics と整合」という暗黙前提を正す。
- **C-3（Must address in design）**：層1ラベルインデックスの semantics を確定（primary type
  のみ＝現状踏襲か、全ラベルか）。マルチラベル／動的ラベルと `list_nodes` の現状挙動
  （primary のみ）との関係を §11 層1 に記述。

## 記録のみ（merge を妨げない）

- §6 に「フィールド統合は MVCC を阻害しないが in-place→CoW 更新規律への移行は別作業」の
  but-clause を追加（方向性は支持）。
- §11.3 の WAL ロールバック保証は「インデックス／directory を全てオンディスクページに置く」
  前提に依存する旨を明記（未決5 の決定と連動）。
- §4 にテストの境界前提（`db.rs:2867` ほか）も改修対象である一行を追加。
- 層3 一意制約の `extends` 継承範囲は実装時決定（plan へ）。

## Conclusion

**approve-with-changes.**

- 容量拡大の主目的（Phase 1–3：page directory・物理解決の置き換え・固定境界撤廃）は設計の
  算術・前提（topology RID の論理性・後方互換放棄・独立 directory）がいずれも実コードと整合
  しており、そのまま進めてよい。
- **インデックス段（Phase 4–6）に入る前に C-1〜C-3 を設計へ反映**すること。特に C-2/C-3 は
  「現状 semantics をインデックスで保てる」という設計の暗黙前提が実コードと食い違う点であり、
  放置すると実装が既存挙動を静かに変える。
- §6 MVCC 統合は判断として支持（最高リスク決定だが coherent）。但し but-clause を添えること。

これらは実装セッションへ差し戻す（本レビューセッションは
`docs/design-variable-topology.md` を直接編集しない）。
