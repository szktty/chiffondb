## Findings addressed

### F-5（Before release）— `push` の `UNMAPPED` 番兵ガード欠如 → ✅ 解決

実装：`push`（`page_directory.rs:105-117`）が先頭で `physical == UNMAPPED` を弾き
`GraphError::StorageCorrupted(physical)` を返す。失敗時に `self.len` を**進めない**
（ガードが `set`/`len += 1` の前にある）。

review-request の3点を実コードで確認：

1. **ガード配置（push が唯一の外部経路か）— ✅ 正しい**。
   - public API surface を grep：mutator は `push`（line 105, `pub`）のみ。`set`（line 123）は
     **private** で `push` からのみ呼ばれる。`write_entry`/`write_link` はモジュール内 free
     関数。→ `push` をガードすれば**全外部経路をカバー**。他にエントリを書く経路はない。
   - `append_blank_dir_page` 内の `write_entry(…, UNMAPPED)` は blank 初期化（全スロットを
     unmapped で埋める）であり mapping 書き込みではない。ガード対象外で正しい。
   - 外部 caller：Phase 1 はスタンドアロンで `push`/`set` の外部呼び出しは未だゼロ
     （grep で確認）。Phase 2 接続時はこのガードが効く。

2. **不変条件の固定 & proptest 非回帰 — ✅**。
   - `push_rejects_unmapped_sentinel`（line 378）：`push(0xFFFF_FFFF).is_err()` かつ
     `len() == 0` を assert。「rejection で len 不変」をピン留め。
   - `push_resolve_roundtrip_multipage` の range は `0u32..1_000_000` で `UNMAPPED`
     (4_294_967_295) に**到達不能**。PROPTEST_CASES=1000 でも 10 passed＝回帰なし。

3. **`StorageCorrupted` variant の妥当性 — ✅**。`set` の既存密度ガード
   （`logical > len` → `StorageCorrupted`, line 130）と**一貫**。コードベースは不変条件破れに
   `StorageCorrupted` を使う方針で、専用 `InvalidArgument` 変種の新設は不要。現状の選択を支持。
   - 補足（記録のみ）：`StorageCorrupted(u32)` のペイロードは「壊れた page id」を意図した
     変種だが、ここでは「拒否した physical 値」を載せている。意味的にはやや転用だが、F-5 の
     ケースは現実到達不能（防御的ガード）であり、診断情報として physical を載せるのは妥当。
     将来 variant を整理するなら検討（plan / Record only）。
